# JFB Field Ops: non-native bugs the native app fixes

## Types

| Type | Meaning |
|---|---|
| Non-native bug | Non-native does it wrong; native does it right |
| Non-native gap | Non-native can't do it, or only through SQL or a code change; native handles it |

## Fixes

| # | Type | Where | Problem | Non-native | How native fixed it | Native files |
|---|---|---|---|---|---|---|
| 1 | Non-native bug | Every long list: report list, dashboard, operator hours, admin lists, Settings tabs, pickers | Lists over 1,000 rows get cut off. | No paging anywhere. Each list loads in one request, and Supabase stops at 1,000 rows without an error. About 8 fetches loop in 1,000-row pages to get past this (e.g. `fetchAllPaged` in `queries.ts`). All other lists, including everything in the admin console, would silently show only the first 1,000. | Server-side paging: 50 rows a page with a page bar on 18 screens. Searchable dropdowns that load page by page: Admin → Team (project and user pickers), Operators (existing-operator picker) and the Capping Setup mapping pickers. Background loads page until done, stop at 50,000 rows, and log a **TRUNCATED** warning if a request comes back full. | `data/index.js`, `hooks/core/useDomainData.js`, `components/PaginationBar.jsx`, `components/ServerPagedSelect.jsx` |
| 2 | Non-native bug | Admin → Equipment → **Edit** | Edit Equipment doesn't load the machine's current values. | The code is a stub, "Load existing data — would need to fetch from Supabase". The form opens with blank or leftover values, and saving writes those over the machine. | The Edit Equipment modal loads the machine's saved values. | `pages/Admin/ProjectDetail/EquipmentTab.jsx` |
| 3 | Non-native gap | Report → **Release** | Nobody knows who released a report. | `report_dates.released_by` exists (a uuid pointing at `user_profiles`) but Release never fills it. Locally, 0 of 711 released reports have it. | Release saves `jfb_reports.released_by_user_id` as the user who clicked it. | `ReportEditorPage.jsx` |
| 4 | Non-native gap | Report → **Download PDF** | A PDF that was sent can't be retrieved later. | PDFs are never saved: `report_dates.pdf_url` is never filled. Every download rebuilds the PDF from today's settings (its CLAUDE.md rule 3). | Each generated PDF is saved as a file and logged in `jfb_report_generations`, with who, when and the file. | `pages/FieldOps/lib/reportDownload.js` |
| 5 | Non-native gap | Daily PDF → dredge, placement and spreader chart pages | Changing a chart setting changes how already-released reports print. | Chart pages are redrawn from the current settings every time the PDF is built. | The PDF uses the chart image saved and approved on that day's report tab. | `reportPdfData.js`, `DredgeProgressTab.jsx`, `PlacementProgressTab.jsx`, `SpreaderProgressTab.jsx` |
| 6 | Non-native gap | Dredge chart files | Anyone with a file's link can open it. | The `dredge-config` storage bucket is public (`getPublicUrl`), a known issue in its CLAUDE.md. | Files are Pivotly attachments, downloaded through the signed-in API (`downloadAttachment`). | `lib/dredge/imageLoaders.js`, `lib/dredge/progressLoaders.js` |
| 7 | Non-native gap | Dredge Chart feature | A new dredging project can't turn the chart on without a code change. | Gated on a hard-coded list of project names in `src/lib/dredge/config.ts`, a known issue in its CLAUDE.md. | A **Show Dredge Chart** checkbox on the project (`jfb_projects.show_dredge_chart`). | `config/dredgeProgress.js`, `AdminProjectsSection.jsx` |
| 8 | Non-native gap | Realized To-Date scopes | A project split into contracts or phases needs a code change. | Scopes are hard-coded per project in `src/lib/realizedScopes.ts` (Kalamazoo, Torch Lake). | Scopes are `jfb_realized_scopes` rows, edited in Settings → **Realized Scopes**. | `RealizedScopesTab.jsx`, `RealizedToDatePage.jsx` |
| 9 | Non-native bug | Event Log after renaming equipment | Renaming a machine hides its old events. | `daily_events` stores equipment, area and operator as text, and the editor filters on the name. Its README lists "Event log shows No events" as the symptom. | Activities point to records by ID (`equipment_id`, area IDs, `operator_id`, `delay_code_id`), so a rename doesn't disconnect them. | domain `jfb_daily_activities` |
| 10 | Non-native gap | Operators | The same person on two projects is two separate records. | `operators` is per project. Cross-project hours rely on `operator_master` and a trigger that matches by name. | One `jfb_operators` record per person, linked to projects through `jfb_project_operators`. **Add Operator** can pick an existing person. | `pages/Admin/ProjectDetail/OperatorsTab.jsx` |
| 11 | Non-native bug | Admin → Users → Add User → **Assigned Project** | The project picked there doesn't give the user access to it. | The console saves it to `user_profiles.project_id`, a legacy column the daily app no longer reads; the daily app reads `user_projects`. The new user sees "No projects assigned" until a `user_projects` row is added by SQL. | Project access is set on Admin → **Team**, which writes `jfb_project_members`, the table the app reads. | `AdminTeamSection.jsx`, `ProjectDetail/TeamTab.jsx` |
| 12 | Non-native bug | Report → Narratives | A section can stay locked after its editor leaves. | Editing a section takes a lock (`locked_by` / `locked_at`), released when the field loses focus. If the editor closes the browser mid-edit, the lock never expires; the planned 10-minute auto-expire was never built. A PM has to click **Release lock**. | No locks. Each save carries a version check. If someone else saved first, native shows an **Update conflict** dialog, so nothing can stay locked. | `pages/FieldOps/reportEditorTabs/NarrativesTab.jsx` |
| 13 | Non-native bug | Report and PDF → Cal / Project / Production week | Week numbers go stale when a project's start date or production start date changes. | Weeks are stored on `report_dates` by a trigger that only fills empty values. After a date change, existing reports keep their old weeks until someone runs the recompute SQL in its README ("Roll back / fix a wrong week number"). | Weeks aren't stored. They're worked out from the report date and the project's dates every time the report is shown or printed. | `pages/FieldOps/lib/reportPdfData.js` (`buildDateTableParams`) |
| 14 | Non-native bug | Any open tab after a deploy | **Download PDF** can fail with "PDF generator unavailable". | The PDF code is a separate file loaded on first click (`await import('../pdf/generatePdf')`). After a deploy that file's old name no longer exists. A handler reloads the page once per session; otherwise the user has to hard-refresh. | The whole app is built into one file (`vite-plugin-singlefile`) and loads nothing separately, so an open tab can't lose part of itself after a deploy. | `vite.config.js` |
| 15 | Non-native gap | Permissions: approve, send back, release, reject photos, override the PDF check, settings, team, operator hours | Changing who can do what needs a code change and a deploy. | Role lists are written in the code: `allowedRoles` per status change in `src/lib/reportStatus.ts`, and route guards in `src/App.tsx`. | Each permission is a named action (`pm_review`, `release_report`, `reject_photos`, `skip_pdf_validation`, `view_deleted_events`, `manage_project_settings`, `manage_team`, `view_operator_hours`, …) granted to roles in Pivotly by `jfb_roles_seed.py`. | `contexts/FieldOpsAccessProvider.jsx`, `pivotly/scripts/jfb_roles_seed.py` |
